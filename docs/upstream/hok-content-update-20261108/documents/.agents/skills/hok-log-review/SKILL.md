# HOK 로그 검토

## 범위와 읽을 자료

사용자의 최신 요청에서 검토 범위를 정한다. 로그 확인 요청은 읽기와 보고만 허용한다. 설명·문서화 전용 요청을 게임 조작, 재현 시험, 설정 변경, 코드 수리, 감시 예약의 승인으로 해석하지 않는다. 별도로 승인된 구현·진단이 있으면 그 범위와 프로젝트 규칙을 따른다.

- 이 스킬이 있는 저장소 루트를 기준으로 [AGENTS.md](../../../AGENTS.md)와 실제 작업 경로를 확인한다.
- 2026-11-06 호환성 수리와 재발을 비교할 때 [구현·검증 기록](../../../docs/incidents/2026-11-06-hok-runtime-compatibility-implementation.md)을 읽는다. 구현 전 오류를 추적할 때는 그 문서에 연결된 구현 전 검토도 읽는다. 과거 시험 결과를 현재 실행의 관측으로 쓰지 않는다.
- 이 PC에서 확인된 로그 경로는 `C:/Users/jaewo/OneDrive/문서/Paradox Interactive/Hearts of Iron IV/logs`다. 실제 사용자 데이터 위치가 바뀌었는지 확인한다. 원본·Workshop·번역 모드 및 외부 증거 자료의 위치와 역할은 위 프로젝트 기록에서 찾고, 현재 로드 상태와 대조한다.

## 현재 실행과 파일 출처 확인

1. `error.log`와 필요한 `system.log`, `game.log`, `setup.log`, `graphics.log`를 읽는다. 버전·체크섬·활성 모드·DLC처럼 확인 가능한 실행 정보를 확보하고, 마지막으로 읽은 로그의 게임 날짜를 보고한다. 파일 수정 시각만으로 현재 게임 날짜를 단정하지 않는다.
2. 반복 행을 오류 종류별로 묶되, 최초·최근 발생 날짜와 다른 오류 직후의 연쇄 관계를 확인한다. 실행 중인 로그는 계속 바뀔 수 있으므로 건수에는 확인 시점을 붙인다.
3. 로그의 상대 경로를 실제 활성 모드의 물리 경로와 대조한다. launcher descriptor와 로드 기록, 해당 파일의 존재, 같은 파일명 덮어쓰기, `replace_path`와 의존 모드 관계를 필요한 만큼 확인한다. 저장소 파일이 곧 현재 로드된 파일이라고 가정하지 않는다.
4. ID나 파일명에 `HOK`·`KOR`가 있는지만으로 걸러내지 않는다. HOK가 원본과 같은 이름으로 제공하는 일본·다른 국가 파일도 확인한다. 반대로 일본·몽골 관련 로그라는 이유만으로 HOK 오류로 분류하지 않는다.
5. 원본 대조는 현재 설치된 정확한 대상 버전의 같은 문맥을 기준으로 한다. 행 번호가 다르면 이벤트·효과 ID와 주변 블록으로 대응시킨다. 원작 Workshop 사본은 역사적 출처이며 현행 문법·정상 동작의 증거로 대신하지 않는다.

## 출처와 원인을 따로 판정

각 오류에서 다음 세 질문을 구분한다.

| 질문 | 필요한 근거 |
|---|---|
| HOK가 제공하는 파일에서 실행됐는가? | 실제 활성 파일과 로그 위치의 대응 |
| HOK 고유 변경 때문에 실패했는가? | 원본과 다른 부분, 호출·scope·인물 소속·flag 등 실패 시 상태와의 연결 |
| 원본만으로도 같은 실패가 재현되는가? | 같은 대상 버전과 조건에서 수행한 원본 대조 실행. 파일 내용이 같다는 사실만으로 대체하지 않음 |

프로젝트의 `CONFIRMED`, `STRONGLY_SUPPORTED`, `UNPROVEN`, `DISPROVEN` 분류를 사용한다. **관측된 오류 발생 자체의 확정**과 **원인 확정**에도 각각 적용한다.

- HOK 파일에서 경고가 나도 HOK 고유 변경이 원인이라고 자동 판정하지 않는다.
- 발생 파일이 원본에만 있거나 효과 내용이 같아도 HOK가 만든 세계 상태·호출 경로의 간접 영향은 별도 질문으로 남는다. 원본 단독 재현 없이 원본 버그로 확정하거나 HOK와 완전히 무관하다고 단정하지 않는다.
- 원인이 불명확하면 가능한 설명과 이를 구분할 관측을 짧게 제시한다. 검토 요청만으로 재현 시험이나 계측을 실행하지 않는다.
- 오류가 없다는 관측은 해당 기능의 등록·실행·실제 효과·UI·저장 호환성 전체를 증명하지 않는다. 실행되지 않은 콘텐츠의 정상 여부를 보증하지 않는다.

## 기존 사례를 사용할 때

다음은 **2026-11-06, HOI4 1.19.4.2에서 확인한 비교 사례**다. 고정 제외 목록이나 미래 실행의 원인 판정으로 사용하지 않는다.

- `common/on_actions/14_sea_on_actions.txt`의 일본 월간 요구: HOK 제공 파일에서 `random_list` 후보가 모두 0이 되는 경고가 기록됐다. 위 구현 기록의 특정 재현 상태에서는 HOK와 현행 원본 조건 모두 후보가 0개였다. 이후 사용자 실행에서 같은 경고가 반복됐다는 사실만으로 그 저장의 일본 flag·세력 단계까지 같은 원인이라고 확정하지 않는다.
- `events/WTT_Japan.txt`의 `wtt_japan.110`: HOK 제공 파일에서 일본–독일 불가침조약 중복 추가 경고가 기록됐다. 당시 해당 효과 블록은 현행 원본과 같았다. 이는 HOK 고유 결함이나 원본 단독 재현을 확정하는 근거가 아니다.
- 몽골·일본 인물, 일본 breach trigger, 한국 해군 연구 보너스, 핀란드 강화 지급, 음원은 위 구현 기록의 수리·검증 범위와 한계를 확인한 뒤 비교한다. 관련 키워드 부재를 한국 콘텐츠 전체의 무결성으로 확대하지 않는다.

## 보고와 산출물

HOK만 요청받으면 HOK 관련으로 확인된 경고와 HOK 원인으로 확인된 결함을 구분해 먼저 보고한다. 귀속이 불명확한 공통 오류를 HOK 결함 목록에 섞지 말고, 범위상 필요한 경우에만 미확정으로 표시한다.

사용자가 “HOK가 원인이었던 로그가 없었지?”라고 물으면 근거 범위에 맞춰 답한다. 예를 들어 **“이번 확인 범위에서 HOK 고유 변경이 원인이라고 확정된 오류는 발견하지 못했다”**는 결론과 **“HOK와 완전히 무관함을 입증했다”**는 결론을 구분한다. 전체 무오류·모든 경로 정상으로 확대하지 않는다.

보고에는 관련 파일·행, 게임 날짜, 실제 영향, 원인 판정과 미확인 범위를 필요한 만큼 포함한다. 원본 전체 복사나 경고를 지우기 위한 효과 삭제를 해결책으로 단정하지 않는다.

읽기 전용 검토에서는 산출물·백업·시험 파일을 만들지 않는다. 별도로 증거 보관·진단이 승인되면 프로젝트 규칙에 따라 `C:/hoi/test/<task-or-run-id>/`를 먼저 정하고 사본·도구 출력을 그곳에 둔다. 활성 로그를 지우거나 회전시키지 않고, 실행 중인 사용자 게임을 종료하지 않는다.
